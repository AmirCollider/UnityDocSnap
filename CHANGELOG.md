# Changelog

All notable changes to Unity DocSnap are documented in this file.

## [1.0.2] - 2026-08-05

Shaping told half the truth. This is the other half, plus a way to throw a snapshot away.

### Fixed

- **Persian in dialogs came out worse than before it was shaped at all.** 1.0.1 prepared every localised string in the Editor, which is right for a label IMGUI draws and wrong for a surface the operating system draws. An `EditorUtility` dialog has a real text stack behind it and has always joined Arabic letters and reordered right-to-left runs on its own; handing it text this tool had already prepared did the work twice, undoing the reordering and leaving presentation forms behind. The backup confirmation and the licence-release confirmation now pass raw text, as they always should have. `DocSnapEditorText.Native` names the rule so the next dialog does not have to rediscover it.
- **A popup was right in exactly one of its two halves.** The closed field of `EditorGUILayout.Popup` is drawn by IMGUI, which joins nothing; the open dropdown is drawn by the platform's menu, which joins correctly by itself. One string array feeds both, so whichever form it carries, one half is wrong — preparing it fixes the field and breaks the list, leaving it raw does the reverse. Every popup in the export window is now drawn as its two halves: a button wearing the popup style with prepared text, and a `GenericMenu` with raw text. Both read correctly, at the same time.
- **A missing glyph for one letter changed the shape of the letter beside it.** Every joining decision reads its neighbours, so a letter the font cannot draw joined reported itself as joining nothing — and the letter *before* it dropped out of its initial or medial shape to match. ر has only two presentation forms, so it is the letter a gap most often lands on, and the damage always showed up on its neighbour: "ر will not attach to the letter before it". Fixed in Unity DirectTMP 1.2.1, which this release's Editor windows use when it is installed.

### Added

- **Delete a snapshot (Pro).** `Unity DocSnap ▸ Export…` grows a **Manage snapshots** section: pick a version, delete it, and its folder goes from disk along with its entry in the registry. One at a time and with a confirmation naming the version, because the shelf is the only copy of every earlier export and a single "delete all" mis-click would take the lot. Once no snapshots are left, a second button clears the output folder — only what DocSnap wrote there; the folder itself and anything else inside it are left alone, because that folder is chosen by the user and `Build/Docs` is the tool's own documented example of one that is shared. Deletion refuses any folder that does not carry the proof DocSnap built it, which is the same proof the output pruner has always required.

  Pro only, and the reason is the shelf cap rather than the deleting: on an edition that keeps three snapshots, a delete button would turn the cap into a speed bump. Pro has no cap, so there is nothing there for it to undermine — it is house-keeping for the tier that accumulates enough snapshots to want some gone. Deleting the folder by hand still works and still leaves the registry counting, which is what stops that being a way around the cap.

  Listed on the exported **Plan** page like every other edition feature, so an export says whether the edition that produced it could do this.

## [1.0.1] - 2026-08-05

A maintenance release. Nine things that were wrong, and one that was missing.

### Fixed

- **The health report filed Unity's own broken references as yours.** A project whose render-pipeline assets live anywhere other than `Assets/Settings` — which is every project that has organised its folders at all — got a report reading "7 broken references in your files", listing seven serialized fields of a URP `Renderer2D.asset` and a `.scenetemplate`. Not one of those fields is reachable from an Inspector: they are written by the template that created the project and broken by Unity's own upgraders. Classification was purely by path, and a path cannot see that. It now also asks what the file IS: an asset whose main type belongs to a Unity render pipeline, to `UnityEditor.SceneTemplate`, or to the handful of other configuration types Unity generates and maintains is Unity's wherever the project files it. Matched on the namespace-qualified type name, so a project's own class that happens to be called `Renderer2DData` is not excused along with it. Separately, the unmistakable vendor folder names — `TextMesh Pro`, `Standard Assets`, `TutorialInfo`, `Editor Default Resources` — now match at any depth, so tidying imports into `Assets/_Game/ThirdParty/` no longer loses the classification; the ambiguous ones (`Settings`, `Plugins`, `Samples`, `XR`) stay anchored to the root of `Assets/`, because those are names people use for their own folders. A vendor folder typed into Project Settings without a leading `Assets/` is now read as a folder *name* and matches anywhere, which is the only useful reading of it.
- **Two console messages on a first export, neither of them about anything.**
  - `EndLayoutGroup: BeginLayoutGroup must be called first.` The Export button ran the whole export from inside the window's own `BeginScrollView`/`EndScrollView` pair, opening modal dialogs and closing the window partway through — so the layout group was never closed. The click is now recorded and acted on after the scroll view has ended, and the export itself is deferred one tick past `Close()`.
  - `No previous export record was found ("Library/UnityDocSnap/manifest_state.json" is missing or unreadable), so stale-file cleanup was skipped…` — printed on the very first export a project ever runs, about a file that has never existed, recommending the exact action the user had just taken. The warning exists for a real case (the record is deleted, a previous export's pages are sitting in the output folder, and the sweep declines to touch them), and it now fires only in that case: when the managed output folders actually hold something.
- **"🚫 Excluded from this export — `UnityDocSnap_Output`".** DocSnap adds one exclude rule of its own, for its output folder on the rare occasion it sits inside `Assets/`. That is the tool keeping out of its own way, not a decision the project made — and reporting it put an "Excluded" card on the dashboard of exports whose honest answer was "nothing was excluded", naming a folder the reader had never chosen to leave out. Derived rules are now applied without being advertised; anything the project actually typed is still listed in full.
- **The same instant, printed three times on the dashboard.** The page header carried a raw UTC ISO string, the Export Info card carried a local stamp with its time zone, and a line below that carried the ISO string again labelled "UTC". The moment is now stated once, in local time with the zone beside it and UTC on hover. `export-info.json` and `export-info.txt` still carry both forms — those are read by programs, and by people six months later, and neither can hover.

### Changed

- **The website moved to `amircollider.com`.** Every link in the Editor and in every exported page — the product page, the licence page, the licence server — pointed at the `workers.dev` hostname the first release shipped with.
- **"Made with 🧋 by AmirCollider" in the exported sidebar links to the author's site**, not to a git history. The page footer already links the repository two lines below, and spells it `github.com/…` so it says where it goes.
- **The dashboard reads as one page again.** "Version V1.0.0" in the Export Info card sat beside a "Unity DocSnap v1.0.0" badge — two unrelated numbers, identical, neither saying which it was; it is now "Export version". "Packages" and "Updatable packages" were dead numbers in the stat grid while a row below repeated the same fact as the clickable one; the tiles are now the links, and the row is gone. The loose full-width rows floating between cards — built from the same control the Scenes and Assets lists use for their *contents*, so the page read as though two asset folders had escaped their card — are now one "More in this export" card.
- **The Packages page is a list you can narrow.** It stated four counts — third-party, Unity, built-in, updates available — and then printed all sixty-odd packages in fixed sections. The only one of those numbers anybody opens the page about is "updates available", and answering it meant reading every card looking for a badge. The tiles are now filters, there is a text filter and a sort (grouped / updates first / name), the built-in engine modules share the same filterable list in a compact form instead of a collapsed block, and the dashboard's "Updatable packages" tile links straight into that state.

### Added

- **Persian and Arabic render correctly in DocSnap's own Editor windows** when the project has [Unity DirectTMP](https://amircollider.com/unity-directtmp) in it. IMGUI joins nothing and reorders nothing, so the Persian translation — which is complete, and correct — was drawn as a row of disconnected letters running backwards in the very window it was written for. DirectTMP's shaping half is pure C# with no Unity types in it, and DocSnap now finds it by reflection and uses it. No assembly reference, no asmdef to edit, and nothing changes for a project that does not have the package: it is one assembly scan per domain and a null check per string. A project that does *not* have it, and has switched the window to فارسی, gets one line saying why — because "the translation is broken" and "your Editor cannot draw it" look identical from where the reader is standing, and only one of them is something they can fix.
- **The exported site points a reader at Unity DirectTMP.** An export of a Persian or Arabic project is read by people who work on that project, in Unity, where TextMeshPro draws their language backwards and unjoined; the tool that fixes that is the one useful thing this page can tell them that is not already in their project. The English and Japanese copy is a line and a link. The Persian copy also names the problem, because only the Persian reader has it.

## [1.0.0] - 2026-07-25

The first stable release, and the one that splits the tool into three editions.

### Added

- **Three editions: Free, Plus and Pro.** Free needs no key, no account and no network: install the package and the entire exporter works — every Scene, every GameObject, every Component, every serialized field, every reference, the project health report, the packages page, full-text search, both visual skins and all three languages. Nothing that worked in 0.11.0 without a licence has been taken behind one, with a single deliberate exception noted below.
- **Plus — $19.99, one-off.** Exactly two things, and they are the two most people come for: the **AI-ready summaries** (`summary/*.md`, `summary/*.json` and the one-paste `summary/ai-bundle.md`) and the **Changes page**. It exists because a great many people want those and have no use whatever for CI automation, file copies or project backups — and asking them to pay $49.99 for two features means most of them buy nothing at all. Paying anything also removes the free-edition line from the exported footer.
- **Pro — $49.99, one-off.** Everything in Plus, plus **unlimited version history** (Free keeps three snapshots, Plus keeps five), **incremental updates** (the lower tiers re-scan everything, exactly as every earlier version did), **verbatim file copies** into `source-files/`, the **whole-project `.unitypackage` backup**, **CI automation** through `DocSnapAPI` and `-executeMethod`, and **your own logo** in the exported sidebar.
- **`Unity DocSnap ▸ Licence & Pro Features`.** One window for both halves of the same question: where a customer pastes the key from their purchase email, and where somebody still deciding reads what each tier adds — with every locked control in the Editor tagged with the tier that unlocks it and its price, so nobody is ever quoted $49.99 for something that costs $19.99. It shows which machine the server knows this Editor as, how long the licence works offline, and a **Release this machine** button so moving to a new computer is self-service rather than a support email.
- **A licence page on the website.** `amircollider.n95pluss.workers.dev/license` does the same seat management from a browser — which is the version that matters when the old machine is dead, sold or wiped, and its Editor is not there to click.
- **`edition` in `export-info.json` and `export-info.txt`.** So a snapshot opened six months later can say why it has no `summary/` folder in it, instead of being a bug hunt.
- **A Plan page (`plan.html`) in every exported site.** Which edition produced this export, what that edition includes, what it does not, and a link to the licence page to check a key against the machines it is active on. Written by all three tiers, including Pro, and linked from the sidebar and the dashboard with the edition name on the chip. The reason it is a page rather than a footer line is that an export outlives the moment it was made: it gets copied to a share and handed to somebody who was not at the keyboard, and "why is there no `summary/` folder in here?" then has no way to be answered from inside the folder. Without it, the honest answer looks exactly like the export having failed halfway - which is the reading somebody acts on. `summary.md` stops advertising the AI summaries, and linking to them, on an edition that does not write them.

### Changed

- **`DocSnapAPI` and `-executeMethod` now require Pro.** This is the one capability that moved behind the licence, and it is also the only gate in the tool that *refuses* rather than quietly doing less. Everywhere else — a Pro checkbox ticked in the Free edition, a Free project at its snapshot limit — the export runs, the unavailable parts are skipped, and the completion dialog lists exactly what was left out. A build agent is different: half-succeeding there means publishing a docs folder that is missing the outputs the pipeline existed to produce, reporting success, and nobody looking again for six months. So a Free Editor fails the call with the reason attached, and `-batchmode` exits non-zero. Every menu item is untouched.
- **The version shelf is capped below Pro: three snapshots on Free, five on Plus.** At the limit an export refreshes the newest folder in place instead of adding another. Plus is deliberately more than Free rather than the same — a paid tier that behaves identically to the free one in a visible respect teaches the customer that paying changed less than they thought. It does not refuse, and it never deletes a snapshot to make room — nothing about a commercial rule should be allowed to destroy somebody's data. The export window says this before the export starts, not after ten minutes of scanning.
- **A version folder is now rewritten to match the plan that produced it.** Clamping the export options decided what a run *wrote*; nothing decided what the folder ended up *holding*, and the two stop being the same question the moment an export lands on a folder that already has content - which is what `Update Previous Export` does by design, what picking an existing version does, and what every export does once the shelf cap is reached. A folder built while Plus or Pro was active kept that tier's `summary/`, `source-files/`, `changes.html` and `project-backup.unitypackage` indefinitely, because the export only ever wrote files and never removed one it had simply not written this time. A Free export onto that folder therefore came out byte-for-byte as complete as a paid one and reported `Project backup: yes` in its own `export-info.txt`. A full export now takes out the artefacts the current edition may not produce, only inside a folder that carries the proof DocSnap built it, and lists every removed file in the completion dialog and the console. An edition that still holds a feature keeps its files untouched when the box is simply left unticked - not ticking something says nothing about wanting the previous run's output deleted - and single-item exports never sweep at all. `hasBackup` and `withFiles` are also checked against the disk before being carried forward, so a snapshot can no longer promise a backup that is not there.
- **A site exported by the Free edition carries one line in its footer.** A credit link and nothing else: no banner, no watermark over the content, no interstitial. An exported site is the customer's work product, and a free tool that defaces the thing you hand your team is one people uninstall rather than upgrade. Any paid edition removes it — including Plus, because telling somebody who paid that they are running the free edition is simply false. Swapping in your own logo is separate, and stays on Pro.

### Security

- **Licence tokens are RSA-signed and verified offline.** Activation returns a token — carrying the tier it was bought at — signed with a private key that exists only in the Worker's encrypted environment; the Editor verifies it against a public key compiled into the package, so after one activation a machine needs no network for 45 days and renews itself quietly whenever it is online. A tier name the build does not recognise resolves to Free rather than to the nearest thing it does know. There is never a licence check in front of an export. Keys are stored server-side only as SHA-256 hashes, so a dump of that database contains nothing usable, and the machine identifier that leaves the Editor is a salted hash of Unity's `deviceUniqueIdentifier` rather than the value itself. Nothing about the project — not its name, not its path, not its size — is ever sent.

## [0.11.0] - 2026-07-25

### Fixed

- **The output folder could be pointed anywhere, including the two places that quietly destroy the work.** `Output Path` in Project Settings was a free-text field with no rules, and `-docsnapOutput` on the command line had none either. Typing `Assets/Docs` — the most natural value there is — put thousands of generated files inside the project: Unity imported every one and wrote it a `.meta`, and then the *next* export walked `Assets/`, found the previous export, and documented it. Each run documented every run before it. Pointing it at `Library/` or `Temp/` was the opposite failure and just as quiet: Unity deletes those, so the snapshot a user believed they had kept was gone by the next launch. The project root itself and any folder *containing* the project were accepted too, which put the one piece of code in the tool that deletes files (`PruneDir`) directly over a user's project. `DocSnapOutputPath` now decides, before an export creates anything: inside `Assets`, `Library`, `Temp`, `Logs`, `obj`, `ProjectSettings` or `Packages` is refused, as are the project root, a folder above it, and a drive root. `Build/Docs` is explicitly still allowed — it is the tool's own documented CI example. Project Settings shows the resolved destination, or the reason it will be refused and a one-click way back to the default; the command line fails the argument rather than the export, so a pipeline stops before opening a single Scene. As a second line, an output folder that somehow still resolves inside `Assets` is added to the exclude filter, so an export can never document its own output.
- **`CleanLegacyOutput` deleted three directory trees without proving it owned them.** `PruneDir` refuses to run in any folder that does not carry the stylesheet DocSnap itself writes; `CleanLegacyOutput`, four lines away in the same file, recursively deleted `assets/`, `assets_ui/` and `files/` with no such check. Two of those three names are names other software uses constantly. It now runs only for a folder that was a DocSnap version folder *before* this export touched it — captured before `PrepareOutput` writes the stylesheet that would otherwise make the proof circular — and re-checks ownership on entry.
- **`.gitignore` and `.gitattributes` still did not exist.** 0.9.1 announced them, 0.10.0 announced them again and added a CI check for them, and neither release actually contained them — so `validate_package.py` has been failing on every push since. Both files now ship. (For anyone uploading through GitHub's web interface: it silently skips dot-files, which is how this happened twice.)
- **Search-result links were escaped but never checked.** Every result href is built from a search record, which is built from a GameObject or asset name that came out of the project. Escaping stopped a value breaking out of the attribute; it did not stop a value *being* a `javascript:` URL. Site links are relative by construction, so `safeHref` now rejects any value carrying a scheme — including the `java\0script:` and `java\tscript:` spellings that browsers accept and a plain prefix test does not catch.

### Changed

- **A language beyond the three built in no longer means editing every renderer.** Which languages exist was spelled out separately in about a dozen places: the sidebar's three hard-coded `<button>` elements, the pre-paint boot script's `lang==='fa'?'rtl':'ltr'`, `app.js`'s own `RTL_LANGS` map and its three-argument `t()`, the export window's `{ "en", "ja", "fa" }` array and its `LangIndex` switch, `NormalizeLang`, and the `data-en`/`data-ja`/`data-fa` attributes emitted by `I18n`. Adding a fourth meant finding all of them, and missing one produced a site that rendered in the new language and then laid itself out as though it were still English. `DocSnapLanguages` is now the only place that knows: the markup grows a `data-<code>` attribute per language on its own, the switcher grows a button, both popups grow an entry, and `app.js` reads the list from the page rather than carrying its own copy. Translations for a language added this way come from `DocSnapTranslations`, a catalogue keyed by the English string, so supplying them touches no renderer — and anything not yet translated falls back to English rather than rendering blank. `validate_package.py` now fails the build if a language code is compared anywhere outside the registry.
- **`data/*.json` is streamed to disk instead of being built as a string first.** The exhaustive JSON of a Scene was `ToString()`-ed into a single string and handed to `File.WriteAllText` — tens of megabytes on a large Scene, on the large object heap, for a document written once and never re-read in the same pass. `JsonValue.WriteTo(TextWriter)` sends the same bytes straight to the file; the manifest, which carries every issue in the project, is written the same way. The output is byte-for-byte identical, which is what `JsonValueStreamingTests` pins down — the incremental update parses these files back, so a writer that drifted from the parser would silently stop reusing unchanged Scenes.

### Added

- **93 more tests.** Every output-path rule including the ones that must *not* fire (`Build/Docs` stays legal, `AssetsExtra` is not inside `Assets`); the language registry driven by registering a language at runtime and asserting the markup follows it; the streamed JSON against the string it replaces, character escaping and all; and the legacy-cleanup guard from both sides — it still cleans a real version folder, and it will not touch one it does not own.
- **Three codebase invariants checked without a Unity licence.** The EditMode job needs a licence a fork cannot have, so it is skipped far more often than it runs — which makes it the wrong place for rules that can be stated textually. `validate_package.py` now fails on a hard-coded language comparison outside the registry, on a fourth recursive `Directory.Delete`, and on the output-folder rule or its export-time gate going missing.

## [0.10.1] - 2026-07-25

### Fixed

- **The Changes page reported a file nobody had touched, on every single export.** `Assets/TextMesh Pro/Resources/Fonts & Materials/LiberationSans SDF - Fallback.asset` sat under **Modified** on the diff of a project that had not been edited, came back the moment it was dismissed, and did it again after the next restart. TextMesh Pro's dynamic font assets carry their glyph table and atlas texture inside the `.asset` itself, and TMP re-serialises the file whenever it renders a character the atlas does not have yet — including while the Editor draws its own UI at startup. Open Unity, close Unity, and the bytes genuinely differ. `HasFileChanged` already preferred the content hash over the size-and-timestamp signature, which correctly stopped reporting files the filesystem had merely touched; it could not help here, because this file really is different. A diff that always contains the same one entry teaches its reader to skim the list, which costs far more than the entry does. Files Unity rewrites on its own schedule are now classified by `DocSnapRegeneratedPaths` and listed in their own collapsed **Rewritten by Unity** group with the pattern that caught each one, out of the headline counts and out of `changes-files/` — separated and stated, never silently dropped, because a diff that quietly omitted a real byte change would be the worse bug. A diff whose only entries are Unity's own churn now correctly reads as "no differences".
- **A malformed command-line argument was ignored in silence.** `Value()` treats a value beginning with `-` as the next argument rather than this one's value, so `-docsnapOutput -docsnapUpdate` could not create a folder literally called `-docsnapUpdate`. Its comment claimed this failed visibly. It did not: the helper returned `null`, the caller's `if (value != null)` skipped the setting without a word, and the export ran to the **default** output folder and reported success. A pipeline pointing its documentation at `Build/Docs` would publish nothing from there and still go green. Every such case now names the offending argument on the console, where a CI log will carry it, and the run is refused outright rather than quietly reinterpreted.

### Changed

- **A CI export no longer rewrites the project's committed settings.** `-docsnapOutput`, `-docsnapExclude`, `-docsnapLanguage`, `-docsnapTheme`, `-docsnapSkin`, `-docsnapNoThumbnails` and `-docsnapNoFonts` went through the ordinary setters, which write `ProjectSettings/UnityDocSnapSettings.json` — the file 0.10.0 introduced specifically so a team could commit it. So every automated run left the working tree dirty with a settings change nobody made, failing the `git diff --exit-code` step a lot of pipelines end with, and on a job that commits its own output it quietly rewrote the project's configuration to whatever that one build happened to pass. A build agent asking for a different output folder for one run is not the same act as a person changing what the project documents, and the two no longer write to the same place: command-line settings now apply to that run only. `-docsnapSaveSettings` opts back into persisting them, for the rare job whose whole purpose is to update the committed file.

### Added

- **Project Settings ▸ Unity DocSnap ▸ Rewritten-by-Unity paths.** The built-in list covers TextMesh Pro's font and sprite assets under both folder names it installs under; a project can add its own in the same pattern syntax `Exclude paths` already uses. Deliberately narrow: lightmaps, NavMesh data and occlusion culling data are regenerated files too and belong nowhere near this list, because they change when somebody presses Bake — which is an authored change and exactly what a Changes page exists to show. The whole value of the list is that a reader can trust what it sets aside, so the page names the matching pattern beside every file it moved.
- **Tests for the two fixes and the classifier.** 34 cases covering `DocSnapRegeneratedPaths` (the reported TMP path, both TextMesh Pro folder spellings, that a Bake-produced lightmap is *not* classified, project-added patterns, cache invalidation), the changes-page split itself (a regenerated file leaves the modified list, an added or removed one is still reported however it is named, and a diff of nothing but churn reads as empty), and the command-line parser (a missing value, a value that is the next flag, a trailing flag, and that session overrides never reach the settings file).

## [0.10.0] - 2026-07-25

### Fixed

- **The cozy skin was the hard one to read.** Pastel is a property of a surface, and this skin had let it into the ink: `#4a3b52` body text with `#b9adc2` labels on a cream background, which is a page you squint at. The lite skin's `--text-faint` was barely better at 2.9:1 against its own surface — under the 4.5:1 anyone needs, and it labels the key in every key/value line on the site. Both palettes now carry darker ink than either did, with the warmth kept where it costs nothing to read: backgrounds, borders and accents. Cozy's body text is now *darker* than the lite skin's, not lighter.
- **The site did not use the window.** Content was capped at 1320px, so a 1920px window had roughly 330px of dead margin beside every page — and on a right-to-left export that strip sat on the left, where it read as the site having failed to load its other half. The page now fills the window; the cap only engages past 1760px, where an unbroken line really is unreadable, and the leftover space is then split evenly rather than piling up on whichever side the writing direction leaves over.
- **Two of the four dashboard tiles were the same colour.** `ds-tile-pink` and `ds-tile-lav` both resolved to `--accent`, so a row meant to be scannable at a glance came out monochrome. There is now a four-hue tile palette per skin, and cozy's is saturated on purpose — a dashboard of pastel numbers is a dashboard nobody reads twice. The headline number is bigger and heavier too; at 27px in a pale hue it had been competing with its own caption.
- **The cozy skin felt machine-made.** The selected language and view mode were marked by a white pill on a white bar, legible only by its shadow, so you could not tell at a glance which one you were in. Both are now filled — coral for language, violet for the view mode, two different questions with two visibly different answers — the current sidebar page gets a coloured rail instead of a slightly different grey, the sidebar's pastel wash holds its colour the whole way down instead of fading to cream above the fold, and card headings finally use the rounded display face the skin ships. Cozy had been applying that face to exactly two elements, which is most of why it read as the lite skin with rounder corners. The mascot mark is larger and its outline darker.
- **`.gitignore` and `.gitattributes` did not exist.** The 0.9.1 notes announced both as Added. Neither was ever committed, nothing checked, and so the release notes stated something untrue for as long as anyone cared to read them. Both files now exist, and `validate_package.py` fails if either goes missing again — along with `LICENSE`, `README.md`, `CHANGELOG.md`, `CONTRIBUTING.md` and `SECURITY.md`. Dot-files are invisible to Unity and were therefore excluded from every other check in that script, which is exactly why they needed their own.
- **The README's privacy claim was false in the default configuration.** "The pixels themselves never leave your project" sat a few lines from a feature that is on by default and writes downscaled PNG previews of your images into `theme/thumbs/`. The tool knew — `DocSnapSettings` even described turning it off as "DocSnap's stricter *pixels never leave your project* mode" — but the README had not been updated to match, in any of the three languages. For a tool whose whole output is meant to be handed to someone else, that is the wrong thing to be wrong about. All three languages now state plainly what an export contains, the Project Settings toggle says the same thing on screen while thumbnails are on, and the README documents the two opt-ins that put real content in an export.

### Added

- **A public API, and a command line.** Everything in the tool was `internal` and every menu handler was `private`, so `-executeMethod` had nothing to call: the one job a documentation tool most obviously belongs in — running on every merge — was the one place it could not go. `DocSnapAPI` is now the package's only public type, with `ExportFullProject`, `ExportScene`, `ExportAssetFolder` and `UpdatePreviousExport`, each returning a `DocSnapResult` that distinguishes success from failure from a user cancelling. `DocSnapAPI.RunFromCommandLine` is the `-executeMethod` target and reads its configuration from the command line (`-docsnapUpdate`, `-docsnapScene`, `-docsnapFolder`, `-docsnapWithFiles`, `-docsnapOutput`, `-docsnapExclude`, `-docsnapLanguage`, `-docsnapTheme`, `-docsnapSkin`, `-docsnapNoThumbnails`, `-docsnapNoFonts`). In `-batchmode` a failed export exits non-zero, so a red build means a real problem.
- **Exports no longer put dialogs in front of nobody.** `EditorUtility.DisplayDialog` is right for someone who just clicked a menu item and wrong everywhere else: in batch mode there is no one to click OK, and the message — often the reason the export failed — is never seen, because the console is the only output a CI log captures. Every user-facing message now goes through `DocSnapInteraction`, which shows a dialog when someone is there and logs the same text when not. Interactive runs are unchanged down to the button labels.
- **Project settings are a file you can commit.** Exclude patterns, not-my-code folders, the output path and the site's defaults describe the *project*, and all of them lived in `EditorUserSettings` — a file Unity documents as per-user data, which carries VCS credentials, and which most studios keep out of version control on purpose. So nobody could commit them, every person on a team configured the exclude list by hand or did not, their exports silently disagreed about what the project even contains, and a CI agent with a fresh checkout had none of it and documented the Asset Store content the team had spent a year excluding. These now live in `ProjectSettings/UnityDocSnapSettings.json`: plain, ordered, one key per line, meant to be read in a pull request. Existing settings migrate once on upgrade, and never over a value the repository already had. Genuinely personal settings — the export window's language, the absolute path to a custom logo — stay exactly where they were.
- **An option to drop the embedded fonts.** They are ~570 KB of base64 and every version folder gets its own copy, which is the right default (an export stays a self-contained thing you can zip and send) and is also 11 MB across twenty snapshots of identical font data. **Project Settings ▸ Unity DocSnap ▸ Embed web fonts** turns it off; the stylesheet already names the system stack after every embedded family, so the layout is unchanged and only the branded face is lost.
- **Tests for the code that turns project data into a page.** `HtmlPageBuilder.Escape`, `JsString` and `Href` are the entire boundary between "the project contains this text" and "the generated page does what that text says", and not one of them had a test — despite the search index shipping as `theme/search-index.js` and being *executed* by every page, which makes every GameObject name in the project a line of JavaScript. 40 new cases cover all three functions, the search index (including that a GameObject called `</script>` cannot end the file it is written into, and that the record cap is announced rather than silent), and the new settings store (round-tripping, diff stability, migration precedence, and that a hand-edited file with a typo is reported rather than silently overwritten).
- **`CONTRIBUTING.md`, `SECURITY.md`, issue forms and a pull request template.** The README had a Contributing section, which is not the same as the files a contributor looks for. `SECURITY.md` is specific about what is actually in scope for this tool: the generated site is code, exports write and delete files, and an export leaves the machine carrying more than metadata when you ask it to.

### Changed

- **A full export no longer holds the whole project in memory.** Pages can only be rendered once the manifest is complete, because a sidebar and every cross-link depend on Scenes exported later in the same pass, and the obvious way to have every Scene's data at the end was to keep it — so peak memory was the entire project's field data at once: every GameObject, every component, every serialized value of every Scene, parsed and live, for as long as the export ran. On a project with a few dozen large Scenes that is gigabytes of managed heap, and the failure mode is the Editor dying partway through a long export. Every one of those trees was already written to `data/*.json`, and `JsonValue` round-trips exactly, so the render pass now reads them back one at a time. Peak memory is one Scene instead of all of them, at the cost of re-parsing files that are almost certainly still in the OS page cache. The whole-`Assets` tree is released before the backup step rather than after, so the two peaks no longer overlap.
- **The log guard filters instead of silencing.** Suppressing URP's "more than one global light" warning was done by setting `Debug.unityLogger.logEnabled = false`, which silences *every* log in the Editor while engaged — including a real `NullReferenceException` from a user's `OnValidate` as a Scene loads, or an error from an unrelated import that happened to land in the same window. A documentation tool losing the user's own errors is a bad trade for a tidier console, and the failure is invisible: the message simply never appears. The guard now installs a log handler that forwards everything except the two messages it can positively identify, counts what it hid, and never suppresses an exception.
- **`FieldRenderer.cs` was the repository's only CRLF file.** With `.gitattributes` now normalising to LF, it is converted once here rather than showing up as a 1,311-line phantom diff the first time anyone else touches it. Every other file in the repository was already LF.
- **`validate_package.py` checks that the newest CHANGELOG entry is the version being shipped.** The old check passed as long as the version appeared anywhere in the file, which stays true forever once a version has shipped — so a release could go out describing itself with the previous version's notes.

## [0.9.1] - 2026-07-25

### Fixed

- **A lost manifest could delete a previous export.** `PruneStaleOutput` keeps each managed output folder holding exactly the files the manifest describes, and deletes anything it does not recognise. Its authority to do that rests entirely on the manifest being the tool's complete memory of the project — and that memory lives in `Library/UnityDocSnap/manifest_state.json`, which is machine-local, git-ignored, and the first thing anyone deletes to make Unity behave. `Load()` answers a missing or corrupt file by handing back a blank state and carrying on, which is right for every other caller and catastrophic for this one: a manifest describing one Scene arriving at a version folder holding twenty made the other nineteen Scenes' pages, data JSON and summaries all "unrecognised", and all deleted. The existing ownership guard could not help — the folder genuinely *is* a DocSnap version folder, which is exactly why it had something worth losing in it. The manifest now records whether it was actually read back from a prior run, and the pruner does nothing at all when it was not, saying so in the console. The version folder is the artefact the user keeps; nothing else in the tool can put it back.
- **Thumbnails accumulated forever.** `theme/thumbs/` was the one managed output folder the cleanup sweep never touched, and the only one that was purely additive: a preview was written as `<guid>.png` and nothing ever removed it. Re-exporting onto a version folder — which **Update Previous Export** does by design, repeatedly — therefore kept a preview for every asset the project had *ever* held, including every one since deleted, renamed or excluded. Nothing links to them, so the folder simply grew, invisibly. The asset index already carries one entry per exported asset keyed by the same GUID, so it is now the live set. A Scene-only export, whose asset index is untouched and empty, deliberately skips the sweep rather than reading "empty" as "none of these are current".
- **Exporting during Play Mode is refused.** An export opens every Scene, and in Play Mode that runs `Awake`/`OnEnable`/`Start` on everything it opens *inside the running game*, while documenting the live simulation — runtime-spawned objects in the hierarchy, serialized values already mutated away from their authored state — rather than the project. Neither half is what anyone asked for, and the first can damage a session in progress. An export started while compiling or importing is refused for the milder version of the same reason: types are being swapped underneath the reflector and the AssetDatabase is mid-write. Both say plainly what to do instead, in all three languages.
- **A custom logo is no longer inlined as markup.** An SVG logo's contents were pasted into every exported page verbatim. SVG is not an image format in the way PNG and JPEG are — it is an XML document that can carry `<script>`, event-handler attributes and external references — so inlining one handed the exported page arbitrary control over itself. The file is the user's own, which makes the practical risk small, but a logo can arrive from a brand kit, a contractor or an asset pack, and the page it lands in is the page a whole team opens. Every format now takes the same route the raster ones already did: a `data:` URI inside an `<img>`, where the browser renders the same picture with scripting and external loads disabled by spec. WebP was added while the format list was being touched.

### Changed

- **The generated site's CSS, JS and fonts are real files again.** They lived in C# verbatim strings: `DocSnapFontAssets.cs` was 582 KB and `DocSnapSiteAssets.cs` 98 KB, together about half of the entire codebase, in a form no C# tool could see into — no linting, no syntax highlighting, no formatter, and every literal double quote written twice. `DocSnapSiteAssets` even carried a note reading "the readable sources they were authored from are plain style.css / app.js; keep the two in step", a manual synchronisation obligation against files that were **not in the repository at all**; there was no way to check it had been honoured and no way for a contributor to find the other half. They now live in `Editor/UnityDocSnap/Site~/` as `style.css`, `app.js`, `fonts.css` and `logo.svg`, read at export time through the new `DocSnapSiteFiles` and cached per domain reload. The trailing `~` is deliberate: Unity ignores such folders completely — no import, no `.meta`, no guessing which importer a `.css` or a `.js` should get — while UPM still ships them exactly like the standard `Documentation~` and `Samples~`. Output is byte-for-byte identical to 0.9.0. Two source files shrank from 680 KB to 4 KB.
- **`preview-sample.html` moved to `Docs~/`.** At the package root it carried a `.meta`, so Unity imported 710 KB of sample output into every project that installed the tool. `Docs~` is invisible to Unity and still ships in the package.

### Added

- **Continuous integration.** `.github/workflows/ci.yml` validates the package on every push with no Unity licence and no secrets — so a fork and a pull request get the same answer the maintainer does — checking version agreement across `package.json`, `DocSnapConstants.Version` and this changelog, `.meta` coverage and GUID uniqueness (a script shipped without its `.meta` gets a fresh random GUID in every user's project, and the author never sees the problem their users get), and that the site assets the exporter reads at runtime actually ship. The EditMode tests then run in a real Editor against Unity 2021.3 (the declared floor) and Unity 6, in a minimal host project assembled around the package. That job checks for the licence secret first and reports "skipped" without it, so a red X always means a real failure.

Ten cases now cover the fresh-manifest refusal, the normal sweep, the ownership guard, thumbnail pruning and its empty-index exception, and the project-wide files that must survive a single-item export. `DocSnapSiteFilesTests` covers the new file-backed site assets, since a missing file is a failure mode a string constant did not have.

Pushing a `v*` tag now publishes a GitHub Release with notes taken from this file, and fails if the tag and `package.json` disagree.

Since versioned exports arrived, the root holds only a redirect and `versions.html`, and the site itself lives in `V1.0.0/`. `versions.html`, `changes.html`, `export-info.txt`, `changes-files/` and the backup were absent entirely, and the only mention of versioning anywhere in the README was a ticked Roadmap box. ## [0.7.0] - 2026-07-24

### Fixed

- **Two Scenes with the same file name no longer overwrite each other.** `Assets/Levels/Main.unity` and `Assets/Test/Main.unity` both wrote `scenes/Main.html`, `data/scene-Main.json` and `summary/scene-Main.md`, so whichever exported second silently replaced the first — while the sidebar showed two "Main" entries pointing at the one surviving page, and both Scenes shared a single search-index scope so re-exporting one wiped the other's records. Output file names now come from a new `DocSnapNaming.SceneKey`, which keeps the plain readable name (`scenes/Main.html`) whenever it is unique in the project and appends a short stable hash of the Scene's path when it is not. The manifest records `sceneKey` alongside `sceneName`; state written by an older version is migrated on load, so previously exported pages keep resolving.
- **Folder keys could collide the same way.** `Assets/UI/Menu` and `Assets/UI_Menu` both flattened to `UI_Menu`. Flattening is only injective while no path segment already contains `_`, so an ambiguous path now carries a hash suffix and every ordinary folder keeps its friendly key.
- **A deep hierarchy took the whole Editor down.** Every other recursion in the tool was capped, but the GameObject walk was not: a deep enough chain (a generated bone rig, a procedural tree) threw `StackOverflowException`, which .NET cannot catch — so every `try`/`catch` around an export was powerless and Unity simply vanished. The walk is now capped at `MaxHierarchyDepth` and marks the node it stopped at; the search index, the anchor map and the health scan were rewritten as iterative walks for the same reason.
- **`Update Previous Export` could not see a renamed file.** The folder fingerprint was file count plus newest modification time, and renaming a file changes neither — so an update reused the entire asset pass and served documentation still describing the old name, with nothing to tell the user. The fingerprint now includes a hash of the file list.
- **A single-Scene export corrupted the version's recorded metadata.** Finalising with fresh defaults rebuilt the version snapshot as if the small export were the whole thing: a version made with *Include file copies* and a `.unitypackage` backup afterwards reported `Included file bytes: no` / `Project backup: no` in `export-info.txt`, lost its 📦 badge on `versions.html`, and dropped the Changes link from the dashboard — while `source-files/`, the backup and `changes.html` all sat untouched in the folder. Facts a run does not re-establish are now carried forward, and a single-item export re-renders in the version's own language and theme instead of resetting to English + light.
- **The reflector truncated nested objects silently.** A struct or `[SerializeReference]` field with more than 1000 members stopped at a bare `guard > 1000` with nothing in the output to say the object was partial — while arrays a few lines away correctly set `truncated`. Both now report it the same way, alongside a `fieldCount`.
- **HDR colours were documented as their dimmed LDR twins.** `ColorUtility.ToHtmlStringRGB` clamps to 0–1, so every emissive tint and bloom-driving light colour lost the intensity that made it interesting. The hex stays for the site's swatches; the exact channel values now travel beside it as `rgba`, flagged with `isHdr` and Unity's own `hdrIntensity` when they leave the displayable range.
- **`NaN` and `Infinity` were written as the number `0`.** A Unity float field genuinely can hold `Infinity`, and reporting it as zero is a documentation tool inventing a value the project does not contain. They are written as `null` now, which every renderer already reads back through `AsNumber(fallback)`.
- **Links broke on ordinary file names.** Half the site built hrefs through `EncodeUrlPath` and half concatenated the raw manifest value into `href="…"`. Those raw ones broke on any Scene or folder whose name contained `&`, `#` or a space — and a name containing a double quote (legal on macOS and Linux) escaped the attribute entirely. Every link now goes through one `HtmlPageBuilder.Href`.
- **HTML escaping was used inside `<script>`.** A browser does not decode entities there, so the value the boot script read differed from the same value read out of the matching HTML attribute — and those two are compared to decide whether a reader's stored language/theme belongs to this export. A proper `JsString` escaper replaced it.
- **One unreadable folder produced an empty export.** `Directory.GetFiles(…, AllDirectories)` abandons the whole enumeration on the first permission error, followed symlinked asset folders into unbounded loops, and counted hidden / `Foo~` / `cvs` folders that Unity itself never imports — so the totals disagreed with the Project window and the change diff listed phantom files. All three filesystem walks now share one `DocSnapFileScan` that skips what it cannot read, caps depth, and honours Unity's own rules.
- **Muting the console leaked.** Call sites set `Debug.unityLogger.logEnabled` directly, so a nested mute restored logging to "on" while an outer one still wanted it off — releasing exactly the warning being suppressed. `DocSnapLogGuard` counts nesting, and every export force-restores the console on the way out so it can never be left silently disabled.
- **Clicking the selected radio button in the export window flipped to the other option**, because both toggles read their return value straight back into the same field and `GUILayout.Toggle` unchecks an already-checked toggle.
- **A rejected custom version name fell through to auto-numbering in silence.** Typing `v1/2` produced a folder called `V1.0.3` with no explanation. The window now says why, both live and before the export starts.
- **`DocSnapConstants.Version` had drifted two releases behind `package.json`** (0.6.2 vs 0.6.4), so every generated `manifest.json`, `export-info.json`, summary footer, dashboard badge and the About window reported the wrong version. A new `PackageVersionTests` fails if the two ever disagree again.

### Performance

- **The preview wait is now budgeted.** Unity renders asset previews asynchronously, and the exporter polled for up to 400 ms **per asset** on the main thread — a project with a few thousand non-image assets could spend well over half an hour inside `Thread.Sleep` with a frozen Editor that looked crashed rather than slow. Waiting now draws down one shared per-export budget; once it is gone the export runs at full speed and falls back to type icons.
- **Assets are loaded once instead of up to three times each**, and unused assets are released every 250 files, so a full export no longer holds the entire project in memory at once.
- **`SerializedObject` and `SerializedProperty` are disposed.** A full export builds tens of thousands of them — one per component, importer and ScriptableObject — and none were released.
- Parsing a data JSON is no longer O(n²) in an object's member count, reading `.Items` on a non-array no longer allocates a list every call, and a script's line count no longer allocates one string per line.

### Added

- **Exports can be cancelled.** Both passes show a cancelable progress bar — the Scene pass previously showed nothing at all, so the slowest half of an export happened behind a completely frozen Editor with force-quitting as the only way out.
- **Exclude rules** (Project Settings ▸ Unity DocSnap, or the export window). One line — `Assets/Plugins` — removes imported Asset Store content from the file walk, the folder tree, the search index, the change diff and the counts at once; `*` and `?` wildcards are supported. The counts now lead, link straight to the pages holding them, and a clean project gets a one-line all-clear.

- **Keyboard shortcuts in the generated site:** `/` or `Ctrl`/`Cmd`+`K` focuses search, `Escape` leaves it.

## [0.3.0] - 2026-07-22

### Fixed
- Asset pages were unreadable when the UI language was switched to Persian. `app.js` sets `dir="rtl"`, but the value spans holding paths, GUIDs, numbers, enums and type names carried no `direction: ltr` / `unicode-bidi: isolate`, so every piece of Latin data was bidi-reordered into fragments. Only `[data-en]` was isolated; the data itself was not. All data-bearing elements are now explicitly LTR-isolated.
- `.ds-asset-grid` used `minmax(300px, 1fr)`. A grid track floor makes the grid wider than its own container whenever the container is narrower than the floor - which is constant inside a nested folder node - so cards overflowed and overlapped. Now `minmax(min(320px, 100%), 1fr)`, with `min-width: 0` on every grid child.
- `.ds-field-grid` had `96px` + `64px` column floors that overflowed narrow cards; `.ds-asset-card`'s `overflow: hidden` then silently clipped the data, which is why Import Settings looked present but unreadable. Floors removed and a container query stacks the grid when a card is genuinely narrow.
- `.ds-tree ul` added 33px of indentation per nesting level, compounding into the two failures above at depth. Indentation now tapers with depth.
- `.ds-kv-line` was a flex row with a non-shrinkable key, so one long path forced the whole card wider than its grid track. Rebuilt as a two-column grid.
- **"Export Full Project With Files" copied every asset's bytes into `files/` and then never referenced them from any page.** No `physicalFile` key was written to the JSON entry and no renderer emitted `<img>`, `<audio>`, `<video>` or a download link, so images and audio never appeared even after a with-files export. Asset cards now play audio and video inline, show the real image file, and expose Open / Download for every copied asset.
- `ThumbnailGenerator.BlitResize` created its RenderTexture with default read/write. In a Linear color-space project this produced gamma-incorrect (washed out or near-black) thumbnails. It now requests `RenderTextureReadWrite.sRGB` when the project is Linear.
- `AssetDatabase.FindAssets(string.Empty, ...)` is undocumented and returns nothing on some Unity versions, producing a silently empty Assets page. `CollectFilePaths` now walks the filesystem and validates each candidate against the AssetDatabase.
- `SanitizeAnchor` collapsed every non-alphanumeric character to `-`, so `UI_Menu`, `UI/Menu` and `UI Menu` all produced the same DOM id. A stable FNV-1a suffix now keeps them distinct.
- `BuildGuidLookup` resolved a GUID indexed under several folders by last-writer-wins, so cross-links pointed at a different page between runs. Resolution is now deterministic, preferring the most specific page.
- `AssetPageRenderer`'s path map was case-sensitive while the folder tree normalised separators, so case drift dropped files out of the rendered tree. Now `OrdinalIgnoreCase`.
- `.ds-matrix-row-head` used the physical `left` property and broke under RTL. Now `inset-inline-start`.

### Changed
- Thumbnails are written as real `assets_ui/thumbs/<guid>.png` files instead of base64 data URIs inlined into both the HTML and the JSON. Previews now lazy-load and cache; a large project's Asset page is no longer a single multi-hundred-megabyte document. Callers that pass no output root still receive the base64 form.
- Import Settings, Fields, Shader Properties and Prefab Contents render inside a collapsed `<details>`. A closed `<details>` is parsed but never laid out, which is the difference between a folder page opening and a folder page hanging the browser.
- Each folder node renders at most `MaxAssetsRenderedPerFolderNode` (300) asset cards, with a count of the remainder. The complete list always remains in `data/assets_*.json`.
- `.tga`, `.psd`, `.exr`, `.tif`, `.webp` and `.bmp` textures - plus Materials, Prefabs, Models and Fonts - now get Unity's real rendered preview via a short polling wait, instead of falling through to a 16x16 type icon. Icons, when still used, are tagged and sized as small badges rather than stretched across the preview box.
- Every generated URL is percent-encoded per path segment. Asset paths containing spaces or `#` previously produced broken links.
- Full-project exports drive an Editor progress bar. They previously ran with no feedback at all and looked frozen.
- Every export prunes scene and asset pages whose source no longer appears in the manifest, instead of leaving orphaned documents behind forever.

## [0.2.3] - 2026-07-08

### Fixed
- Nested/jagged numeric arrays (vertex lists, matrices, per-bone weight tables, …) could still split a value mid-character (e.g. `0.399261` into `0.39` / `9261`) despite the 0.2.1/0.2.2 fixes, because `.ds-nested-table`'s nested `<table>` and `.ds-array-item`'s `overflow-wrap: anywhere` could still be squeezed into a narrow column once enough levels of nesting compounded a fixed percentage width. - `RenderShaderProps` (Material shader property tables) now shares the same field-grid renderer as every other field table instead of its own separate `<table class="ds-field-table">` markup.

### Added
- Jagged/2D scalar arrays (an array whose own elements are arrays) are now detected and rendered as one real, sticky-header, horizontally+vertically scrollable spreadsheet-style table (`.ds-matrix-scroll` / `.ds-matrix-table`) instead of nesting an array block inside another array block - this specific shape of data was the actual root cause behind the character-splitting bug recurring after every previous patch.
